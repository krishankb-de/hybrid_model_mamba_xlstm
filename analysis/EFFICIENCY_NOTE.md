# Efficiency: did the Triton work pay off, and where do we stand against FlashAttention?

> Written 2026-09-25 (`EFFICIENCY_PLAN.md` E5-A) in answer to a supervisor question of the same
> date. Every number here is measured on this project's H100 nodes with randomly initialised
> weights and random token ids; throughput and memory do not depend on weight values, so no
> checkpoint, no MIMIC data and no reported quality metric is involved. Jobs 2579631, 2579642,
> 2580198, 2582482, 2582775. Where an earlier number in this repository disagrees with one here,
> the reason is stated rather than the older number quietly replaced.

## The question

> "I also find out the throughput of our method is still behind some state of the art model who use
> FlashAttention of transformers. I saw some code you use Triton or something else to empower mamba
> be compatible with FlashAttention attributes. Did it work out?"

## The short answer

**No hand-written Triton kernel was ever part of this project, and none was needed.** The premise is
understandable but incorrect, and §1 explains exactly which files created that impression. The
throughput observation was correct when it was made. It is no longer correct: on the corrected
operator, with `torch.compile` enabled for inference, **this model is now faster than the
parameter-matched FlashAttention Transformer at both 8,192 and 16,384 tokens**, at equal memory.

## 1. The Triton premise, checked against the repository

`scan_triton.py` and `tfla_triton.py` existed. Between them they had **one call site**, inside
`mamba_block_v2.py`, which was imported only by two other modules that the live model never loads —
`hybrid_block.py` dispatches to `MambaBlock`, not the v2 variant. So the Triton path could not have
executed in any run that produced a published number. All of it was deleted in commit `37f7964`, and
`scan_interface.py:28` has read `TRITON_AVAILABLE = False` since.

Four artefacts made the repository look otherwise. All four are removed as of this note (E5-C, with
a regression test so they cannot come back):

| artefact | what it implied |
|---|---|
| `test_triton_fix.py` at the repo root | a stale Colab-era script whose docstring read "Test script to verify the Triton kernel fix" |
| `triton>=2.1.0` in `requirements.txt` and `requirements-colab.txt` | a dependency nothing imported |
| `hybrid_xmamba/__init__.py` | advertised "custom CUDA/Triton kernels" |
| `train_biomedclip_kd_h100.sh` | credited "the same custom Mamba/mLSTM Triton kernels" |

There is also a naming coincidence worth stating plainly: **TFLA** stands for *Tiled Flash Linear
Attention*. The word "Flash" is in the name because the algorithm borrows FlashAttention's tiling
idea. The implementation here is chunk-parallel matrix multiplication in ordinary PyTorch.

**One nuance that matters, and that makes the answer less tidy than "no".** Triton kernels *do* run
in this project now — generated by PyTorch Inductor when the model runs under `torch.compile`. That
is an opt-in inference path added in E1, not a kernel anyone here wrote. So the accurate sentence is:
*we never hand-wrote a Triton kernel; we now let the compiler write them for us, and that is what
closed the gap.*

## 2. Was the gap the algorithm or the kernel? Measured, not argued

The standing explanation in this project's writeup was that `F.scaled_dot_product_attention`
dispatches to a fused kernel while our scan was interpreted PyTorch. That was an assertion. It is now
a measurement: the same Transformer, the same protocol, with only the SDPA backend changed
(batch 4, bf16, H100).

| sequence length | fused (FlashAttention) | unfused (PyTorch `math`) | fused advantage |
|---|---|---|---|
| 2,048 | 16.12 ms / 1.24 GB | 81.93 ms / 2.43 GB | 5.1× |
| 4,096 | 33.32 ms / 2.09 GB | 298.79 ms / 8.11 GB | 9.0× |
| 8,192 | 71.34 ms / 3.78 GB | 1195.95 ms / 30.45 GB | 16.8× |
| 16,384 | 163.86 ms / 7.15 GB | **out of memory** | runs vs does not run |

Latency exponent 0.871 fused against **1.513** unfused; memory exponent 0.644 against **1.201**.

So FlashAttention is worth up to 16.8× and, at 16,384 tokens, the difference between running and not
running. **Against the same attention algorithm without its hand-written kernel, our model was
already roughly 3× faster at 8,192 and ran at 16,384 where that baseline could not.** The deficit was
kernel engineering, not the architecture.

## 3. Where the time actually went

At 16,384 tokens, of the Mamba-3 model's forward pass:

| component | share |
|---|---|
| the 9 Mamba-3 layers | 77.8% |
| — of which inside `ssd_chunked_scan` | 67.5% of the whole forward |
| the 3 mLSTM layers | 13.4% |
| embedding, head, norms | 8.8% |

The cause was structural: `ssd_interface.py` carried chunk state in a Python `for` loop, and at
`chunk_size=64` a 16,384-token forward ran 256 iterations per layer, 2,304 across the model, each
launching small kernels. The Transformer issues one fused call per layer.

## 4. Two changes, both verified to compute the same function

Neither is a new algorithm. Both are inference-time settings.

- **`mamba3_chunk_size` 64 → 128.** Fewer, larger chunks. The chunked decomposition is exact at any
  chunk size. Worth ~1.40× on its own.
- **`torch.compile` on the inference path.** The project pins `compile_model=false`, for a reason
  documented against the *Mamba-1* block's document-boundary loop — a reason that never applied to
  SSD and had not been re-tested since. Worth 3–5×.

**Correctness came first, because this project has shipped a wrong operator before.** The selective
scan's `A_cum.clamp(1e-8)` defect had a relative max error of 0.92, and repairing it is what the
whole Mamba-3 campaign was for. So every variant here had to pass an equivalence gate before its
speed was allowed to count: agreement with a float64 sequential oracle, including across a packed
document boundary falling inside a chunk. Measured on the H100: operator agreement **2.1e-07**,
model logits **2.3e-05 to 3.4e-05**, `torch.compile` logits **3.0e-05**, against a **1e-4** tolerance
fixed in advance. No variant changes what the model computes.

## 5. Where we now stand against FlashAttention

Inference, batch 4, bf16, each point measured in its own process with its own compiler cache:

| sequence length | Transformer (FlashAttention) | ours (compiled, `chunk_size=128`) | |
|---|---|---|---|
| 8,192 | 71.26 ms / 3.776 GB | **62.09 ms / 3.824 GB** | **1.15× faster** |
| 16,384 | 164.85 ms / 7.152 GB | **122.90 ms / 7.169 GB** | **1.34× faster** |

Memory is at parity — 0.24% higher at 16,384 — where the previous generation of this model needed
42 GB at that length against FlashAttention's 7.15 GB.

The scaling is the part worth putting in a thesis. From 8,192 to 16,384 tokens our latency exponent
is **0.985** and attention's is **1.210**. Ours is linear in sequence length, as the architecture
predicts; attention's is not, and the advantage grows with length.

## 6. What is *not* claimed

- **Memory parity is an inference result only.** In training we use **12.02 GB against the
  Transformer's 7.55 GB at 2,048 tokens — 1.59× more** — even compiled. That gap is unchanged by
  this work.
- **Training is still slower**, though much less so: the deficit at 2,048 tokens falls from 5.86× to
  **2.71×** with compile and `chunk_size=128`, and at 1,024 tokens from 8.74× to 1.23×.
- **The older "8× slower training at L=2,048" figure does not reproduce.** The measured baseline here
  is 5.86× on a 5-iteration protocol. The discrepancy is unexplained; the older number should not be
  re-quoted without re-measurement.
- **`torch.compile` is opt-in, not the default.** It costs a few seconds of graph build per sequence
  length and slightly more inference memory, and no training configuration in this project turns it
  on. The uncompiled default-path number at 16,384 is 562 ms / 7.090 GB.
- **None of this changes a single quality metric.** Every reported ROUGE-L, BLEU and CheXbert number
  stands exactly as published.

## 7. An error in this project's own measurements, and how it was caught

The first version of these numbers gave every profiling arm a shared Inductor compiler cache, to
avoid paying the same graph build twice. That sharing corrupted the results it was meant to speed up:
two arms with *different* chunk sizes were handed the same compiled kernel and timed identically to
one microsecond at 4,096 tokens. Re-measuring with per-arm caches made the same points 21–30% faster.

A second effect was larger: within a single process, shapes compiled *later* measured worse — the
compiled training arm ran 3.04× at 512 tokens and 1.02× by 4,096.

Both are fixed by the protocol in §5: **one sequence length per process, one compiler cache per
point.** The headline reproduced to 0.2% under it (122.90 vs 122.68 ms), and the 8,192 result
*improved* from 0.80× behind to 1.15× ahead. A scaling exponent of 0.47 that appeared in an interim
note was an artefact of the contaminated 8,192 point and has been withdrawn; 0.985 is the correct
figure.

The anomaly was caught because the profiler reports the chunk size read back **off the built module**
rather than echoing the requested value, which distinguished "the setting never arrived" from "the
setting arrived and did not matter" in a single run.
