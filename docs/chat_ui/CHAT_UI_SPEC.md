# CXR Report-Generation Chat UI — Multi-Phase Plan

Sep 30, 2026 · @Krishan

## 1. Goal, scope and the constraints that shape it

Build a Claude-style chat front end for the thesis model: a user drops a chest X-ray (plus an optional prompt or reference report), watches each stage run — preprocessing, image encoding, retrieval, beam-search generation, CheXbert labelling, scoring — and gets a stored, replayable, exportable session. Local first, then a hosted demo, at zero cost.

**In scope**

- Single-image report generation with the published decoder: `hybrid_150m_m3_rrg` + `outputs/h100_report_gen_m3_tower13d_s42/checkpoints/last.ckpt` as the default (it supports the O(1) cached decode, so CPU serving is realistic), the 13D incumbent (`hybrid_150m_v2_rrg`) as a selectable second model (uncached path only).
- Image retrieval shown with images (§6a): similar training X-rays (image→image) and best-matching reports (image→report) from the retrieval chapter's 13D joint checkpoint, with the uploaded image and the model's 224×224 input displayed in the chat; CheXbert-14 labels of the generated report; ROUGE-L / BLEU / CheXbert metrics when the user supplies a reference report.
- Per-stage timings and full provenance on every answer (model, checkpoint hash, operator flags, `prefix_k`, git SHA, torch version, decode settings).
- Sessions: create, list, replay, export (JSON + Markdown), delete. Settings drawer for beam size, token budget, cached decode, `torch.compile`, retrieval k, mode.
- A laptop dev loop that needs no weights and no data (tiny random-init model, the repo's existing `--smoke-test` pattern).

**Out of scope (for now)**

- Free-form question answering about the report. The model is a report generator, not an instruction follower; the UI says so, and a follow-up text turn without a new image is treated as a command (re-run with other decode settings, compare to a reference), not a question.
- Training, DICOM/PACS integration, user accounts, paid hosting or cloud GPUs.

**The three constraints every decision below follows**

1. **Data-use agreement.** The checkpoints and everything retrieved from MIMIC are Class R in `analysis/ARCHIVE_MANIFEST.md`: they stay on the cluster or approved storage. So inference runs only where the weights already live; the browser only ever receives generated text and derived numbers. Retrieved report text, study ids and reference reports are shown only in *private* mode (you, on the cluster, or a credentialed viewer). Nothing MIMIC-derived is ever committed to GitHub or copied to a laptop or free cloud tier — which rules out Hugging Face Spaces, Colab and Streamlit Cloud for the model server.
2. **Cluster rules.** The `lx01` login node executes nothing scripted, so the server is an `sbatch` job; a CPU-only allocation is enough (see §8). Compute nodes have no internet, so BiomedCLIP, the GPT-2 tokenizer and the CheXbert weights are pre-staged and every process runs `HF_HUB_OFFLINE=1`. `aisc-batch` is preemptible, so the job requeues itself and the laptop-side tunnel re-discovers the node.
3. **Zero cost.** FastAPI + SQLite + vanilla HTML/JS (no build step, no framework), `ssh -L` from the laptop to the compute node, a free Cloudflare quick tunnel for a public URL, GitHub for code and optionally GitHub Pages for the static UI. No paid service anywhere in the stack.

**Estimate.** Eight phases, about 12–16 working days part-time; the first usable local demo (P0–P4 on the tiny model) lands after roughly a week.

## 2. How it is done elsewhere, and what this design borrows

Every production chat assistant separates a thin browser client from a streaming HTTP API; medical report-generation demos are almost all Gradio apps on Hugging Face Spaces. This design takes the assistants' API shape and the demos' medical-UI conventions, and departs from both where the data-use agreement forces it.

**Chat assistants (Claude, ChatGPT).** The client is a single-page app that sends one HTTP request per turn and reads the answer as a stream. Anthropic's Messages API streams typed Server-Sent Events over a `POST`: `message_start`, then one or more content blocks each bracketed by `content_block_start` / `content_block_delta` / `content_block_stop`, then `message_delta` and `message_stop`, with `ping` keep-alives and `error` events ([Anthropic docs](https://docs.anthropic.com/en/api/messages-streaming)). What we borrow: the same envelope and vocabulary, plus one addition — `stage_start` / `stage_end` events for the pipeline stages, so the client renders a timeline rather than only a text stream. What we drop: multi-turn conversation semantics; each turn here is an image plus options.

**Radiology report-generation demos.** The public examples are Gradio Spaces: a CPU-only findings generator with an attention explorer ([CXR-Findings-AI](https://huggingface.co/spaces/manu02/CXR-Findings-AI)), an editable-report generator "to assist radiologists" ([Chest X-ray Auto Report Generator](https://huggingface.co/spaces/Neemah/Chest_X-ray_Auto_Report_Generator)), a MedGemma wrapper that spells out its research-only disclaimer and its lack of DICOM support ([MedGemma Radiology Report Generator](https://huggingface.co/spaces/jbondy007/MedgemmaRadiology)), CheXagent's own `demos/app_demos.py` ([CheXagent](https://github.com/thedatasense/CheXagent)), and the tool-using MedRAX agent ([MedRAX](https://github.com/bowang-lab/medrax)). Conventions worth keeping: a visible "research use only, not for clinical decisions" banner on every answer; the report shown as editable text with a copy button; a classification panel next to the prose (here: CheXbert-14 labels); PNG/JPEG input only, with DICOM converted client-side or rejected with a clear message; CPU inference is normal for models of this size. Why not simply ship a Gradio Space: Spaces host the weights, which the DUA forbids, and Gradio cannot show a per-stage timeline or replay a stored session. Gradio remains the one-day fallback for an internal demo.

**Free public exposure.** A Cloudflare quick tunnel gives a laptop port an HTTPS URL with one command and no account (`cloudflared tunnel --url http://localhost:8000`, [try.cloudflare.com](https://try.cloudflare.com)). Its documented limits shape the transport: 200 requests in flight, no uptime guarantee, and `GET` responses are buffered until complete while `POST` responses stream as written — so browser `EventSource` (always `GET`) freezes and then dumps everything, but a streamed `POST` read with `fetch()` works ([measured guide, Sept 2026](https://flaviocopes.com/cloudflare-quick-tunnels/)). Decision: stream over `POST` + `fetch()` only, never `EventSource`, and keep a polling endpoint as the fallback. A named tunnel (free account + a domain on Cloudflare DNS) removes these limits and adds a login page; it is the upgrade path if a domain is ever available.

**What the DUA changes versus all of the above.** The model server never leaves the cluster; the browser receives generated text and derived numbers only; retrieved MIMIC reports, study ids and reference texts appear in private mode alone. No public demo elsewhere had this constraint, so none of the hosted patterns (Spaces, Colab, Streamlit Cloud) transfer.

## 3. Architecture

Four processes, one of them optional: a static single-page app in the browser, the FastAPI server and the CheXbert labeler inside one `sbatch` CPU job on the cluster, and the laptop acting only as a tunnel endpoint. The model, the gallery, the uploads and the session database never leave `/sc/home`.

[embedded content: deployment topology · browser, laptop tunnel, one cluster job]

Requests enter from the left and stay inside the cluster box: the browser talks to the laptop's forwarded port, the laptop forwards to the compute node, and FastAPI fans out to the engine, the gallery, the labeler and the store.

**Components**

| Component | Runs where | Built from | Talks to |
| --- | --- | --- | --- |
| SPA (`app/static/`) | browser | vanilla HTML/CSS/JS, no build step | FastAPI over `fetch()` |
| FastAPI server (`app/server.py`) | cluster CPU job, port 8000 | FastAPI + uvicorn, stdlib `sqlite3` | engine (in-process), labeler (HTTP localhost:8001), SQLite |
| Inference engine (`app/engine.py`) | same process as FastAPI | `evaluate_report_generation.load_report_generation_module`, `HybridLanguageModel.beam_search_cached` | BiomedCLIP tower, decoder, gallery memmap |
| Retrieval gallery (`app/gallery.py`) | same process | precomputed `.npy` of 191,462 pooled BiomedCLIP embeddings + a study-id index | engine |
| CheXbert labeler (`app/labeler.py`) | second process in the chexbert venv, port 8001 | `f1chexbert` (transformers<5, scikit-learn<1.8) | FastAPI |
| Store (`app/store.py`) | same process as FastAPI | SQLite file + `uploads/`, `generations/` directories under `/sc/home/$USER/chat_sessions/` | FastAPI |
| Tunnel scripts (`app/tunnel/`) | laptop | `ssh -L`, optional `cloudflared` | compute node |

**One request, end to end.** The SPA `POST`s the image plus options; FastAPI writes the user message, then runs the pipeline on a single-worker executor and emits events as each stage completes: `preprocess` (resize 224, grayscale to 3 channels, BiomedCLIP normalisation — the published transform), `encode` (ViT patch grid 197×768 → pooled 512-d embedding and the 32-token prefix), `retrieve` (cosine top-k against the gallery), `generate` (cached beam search, the best beam's partial text streamed per step), `label` (CheXbert-14 on the generated report), and `score` only when a reference was supplied. Every event is appended to the store before it is sent, so a session replays exactly what the client saw.

**Private vs public mode.** One server flag, `--mode private|public`, decides what leaves the cluster. Private (default when you are the only viewer) returns everything: retrieved report text, study ids, reference reports and their metrics, the test-split browser. Public strips retrieved text and ids to similarity scores and label vectors, disables the test-split browser, requires the bearer token, and caps uploads and rate. The mode is stamped into every stored message so a session cannot be misread later.

**Why one CPU job and not a GPU.** The published decoder has an O(1) recurrent cache that is token-identical to the uncached beam search by test (MAMBA3\_PLAN\_V2 M6-D, V4); a 132-token beam-3 decode is about 100 single-token steps of a 184M-parameter model plus a 32-step prefill, which is seconds on 8 cores, and the ViT-B/16 forward on one 224² image is under a second. A GPU buys nothing a demo needs and would hold an accelerator idle between requests.

## 4. API contract

Eleven endpoints under `/v1`, one of which streams. Every response carries `X-Request-Id`; every non-`GET` requires `Authorization: Bearer <APP_TOKEN>` (the token is an environment variable on the server; in private mode on `localhost` it may be empty). FastAPI publishes the OpenAPI document at `/docs` and `/openapi.json`, so the contract below is also the generated reference.

| Method + path | Purpose | Body / params | Returns |
| --- | --- | --- | --- |
| `GET /healthz` | liveness; used by the tunnel script and the UI banner | — | `{"status":"ok","model_loaded":true,"labeler":"ok","gallery":"ok","mode":"private"}` |
| `GET /v1/models` | provenance of the loaded model(s) and gallery | — | model card (§5) + gallery manifest (§6a) |
| `POST /v1/sessions` | new session | `{"title"?: str}` | `{"id":"s_01J…","created_at":…,"mode":…}` |
| `GET /v1/sessions` | list sessions | `?limit=50&cursor=` | `{"sessions":[…],"next_cursor":…}` |
| `GET /v1/sessions/{id}` | full transcript incl. stage events | — | session + messages |
| `DELETE /v1/sessions/{id}` | delete session, its uploads and dumps | — | `204` |
| `POST /v1/sessions/{id}/messages` | **the streaming turn** (multipart) | `image` file, `text`, `options` JSON | `text/event-stream` (below) |
| `GET /v1/messages/{id}` | one message with all stored events | `?after=<seq>` for polling | message + events |
| `GET /v1/messages/{id}/image` | the turn's image, served back (§6a) | `?variant=original\|thumb\|model_input` | `image/png` or `image/jpeg` |
| `GET /v1/gallery/images/{row}` | a neighbour's thumbnail; private mode only | — | `image/jpeg`, `no-store`; `403` in public mode |
| `POST /v1/retrieve` | both retrieval views without generating | multipart `image`, `k_images`, `k_reports` | `image_neighbors`, `report_matches` |
| `POST /v1/label` | CheXbert-14 on arbitrary text | `{"text": str}` | 14 labels |
| `GET /v1/sessions/{id}/export` | download | `?format=json\|md` | file |

**Request: one turn.** Multipart because the image is binary; `options` is a JSON string. Defaults reproduce the published protocol exactly.

```bash
curl -N http://localhost:8000/v1/sessions/s_01J8K/messages \
  -H "Authorization: Bearer $APP_TOKEN" \
  -F image=@study.png \
  -F text="frontal view, compare to reference" \
  -F 'options={"model":"hybrid_150m_m3_rrg","decode":"beam","beam_size":3,
               "max_new_tokens":100,"cached_decode":true,"compile":false,
               "retrieval_k":3,"label":true,"reference":null,"display_repair":false}'
```

| Option | Type, default | Meaning and bounds |
| --- | --- | --- |
| `model` | `hybrid_150m_m3_rrg` | or `hybrid_150m_v2_rrg` (13D incumbent, uncached only) |
| `decode` | `beam` | `beam` or `greedy` |
| `beam_size` | 3, range 1–8 | published protocol is 3 |
| `max_new_tokens` | 100, range 16–200 | published budget is 100; V5-E measured 200 as worse |
| `cached_decode` | `true` | the O(1) recurrent path (token-identical by test); `false` = the published uncached loop |
| `compile` | `false` | `torch.compile` on the decoder; verified on decoded text (E7); a server-level allow-list can disable it |
| `k_images` | 4, range 0–12 | similar training X-rays (image→image, §6a); 0 skips it |
| `k_reports` | 3, range 0–10 | best-matching reports (image→report, §6a); 0 skips it |
| `label` | `true` | run CheXbert-14 on the generated report |
| `reference` | `null` | reference report text; enables the `score` stage (private mode only) |
| `display_repair` | `false` | drop a severed trailing fragment for display only; the raw report is always stored (V5-D showed trimming does not improve metrics) |

**Response: the event stream.** `Content-Type: text/event-stream` over the `POST` connection, read with `fetch()` and a `ReadableStream`. Same envelope as the Messages API, plus stage events. Field `seq` is a per-message counter so a client that disconnects resumes with `GET /v1/messages/{id}?after=<seq>`.

In public mode the `retrieve` detail contains `similarity` only, `score` is refused with `403`, and `reference` is ignored with a warning event. Errors use `event: error` with `{"type":"error","error":{"type":"validation_error|model_error|overloaded_error","message":…}}`; `overloaded_error` is returned when the single-worker queue exceeds its length (default 4) and maps to HTTP `429` on the non-streaming endpoints.

**Polling fallback.** `GET /v1/messages/m_01J8KX?after=57` returns the events with `seq > 57` and the message status (`running|done|error`); the client polls every 500 ms whenever the stream has produced no bytes for 3 s. This is what keeps the public demo usable through a quick tunnel.

**Text-only turns.** A turn without an image is accepted only when the session already has one: the text is parsed for a small command set (`beam 5`, `greedy`, `tokens 150`, `retrieve 5`, `reference: <text>`, `repair on`), the previous image is reused, and the pipeline re-runs. Anything else is answered with the fixed message that the assistant generates reports and does not answer questions.

## 5. Inference engine walkthrough

The engine is a thin class over code the repo already has; the only change inside `hybrid_xmamba/` is an optional `on_step` callback on `beam_search_cached`, defaulting to `None`, with a parity test that its output is unchanged. Everything else imports from `scripts/evaluate_report_generation.py` and `scripts/bootstrap_compare.py`.

**Load once, at process start.**

```python
# app/engine.py (sketch)
import hashlib, json, subprocess, time, torch
from pathlib import Path
from transformers import AutoTokenizer
from scripts.evaluate_report_generation import (
    load_report_generation_module, beam_search_decode, rouge_l_score, corpus_bleu)

class Engine:
    def __init__(self, ckpt, model_config, device="cpu", threads=8, chunk_size=None):
        torch.set_num_threads(threads)
        self.module = load_report_generation_module(
            ckpt, model_config, device=device, chunk_size=chunk_size)   # prints [operator] overrides
        self.tok = AutoTokenizer.from_pretrained("gpt2")               # HF_HUB_OFFLINE=1, cached
        self.card = self._provenance(ckpt, model_config)

    def _provenance(self, ckpt, cfg):
        meta = Path(ckpt).resolve().parent.parent / "run_metadata.json"
        return {"model": cfg, "checkpoint": str(ckpt),
                "checkpoint_sha256": hashlib.sha256(Path(ckpt).read_bytes()).hexdigest(),
                "prefix_k": self.module.prefix_k,
                "scan_impl": self.module.decoder.config.scan_impl,
                "tfla_impl": self.module.decoder.config.tfla_impl,
                "mamba3_chunk_size": self.module.decoder.config.mamba3_chunk_size,
                "train_run_metadata": json.loads(meta.read_text()) if meta.exists() else None,
                "torch": torch.__version__,
                "git_sha": subprocess.run(["git","rev-parse","HEAD"],capture_output=True,text=True).stdout.strip(),
                "cached_decode_available": self.module.decoder.supports_cached_decode()}
```

**Stages, in order.** Each is a method that returns `(detail: dict, ms: float)`; the server wraps them and emits events.

1. `preprocess(bytes)` — PIL open, convert RGB, `T.Resize((224,224))`, `T.Grayscale(3)`, `ToTensor`, CLIP mean/std: byte-for-byte the transform in `run_checkpoint_inspection` and in the training dataset (no augmentation). Reject anything that is not PNG/JPEG/WEBP, larger than 20 MB, or smaller than 64×64. DICOM is converted in the browser (Phase P4) or rejected with a message.
2. `encode(pixel_values)` — `patch_grid = module._patch_grid(px)` (197×768, pre-pooling) and `pooled = F.normalize(module.image_encoder(px), dim=-1)` (512-d) in one `torch.inference_mode()` block; `prefix = module.prefix_mapper(patch_grid)` (32×768). The tower is the checkpoint's own image encoder (the 13D tower weights loaded into the BiomedCLIP visual module), not stock BiomedCLIP.
3. `retrieve(pooled, k)` — cosine against a `float16` memmap `gallery.npy` (191,462×512, \~196 MB) built once by `scripts/build_retrieval_gallery_h100.sh` with the same tower; `gallery_meta.parquet` maps rows to `study_id`, `subject_id`, `findings`, `impression`, `report_hash`. The gallery file records the tower's SHA-256; the engine refuses a gallery embedded with a different tower. Public mode returns similarities only.
4. `generate(prefix, options)` — the published path: `input_ids = torch.zeros((1,0), long)` (no BOS, exactly as training), `beam_search_cached(input_ids, prefix_embeds=prefix, beam_size, max_new_tokens, on_step=cb)`; `cb(step, best_ids)` fires once per decode step and the server turns it into a `beam_snapshot` delta. `cached_decode=false` or the 13D model (no `step()` for Mamba-1) falls back to `beam_search_decode`; `greedy` uses `generate(top_k=1)`. Decoding runs in fp32 with no autocast, as every published number did. Records `prefill_ms`, `per_token_ms`, `stopped="budget"` (there is no end-of-report token in the training targets, so every report stops at the budget — stated on the card).
5. `label(text)` — `POST http://127.0.0.1:8001/label` to the labeler service, 10 s timeout; on failure the stage ends with `skipped: labeler_unavailable` and the answer is still delivered. The labeler is a 60-line FastAPI app in the chexbert venv that keeps one `F1CheXbert()` warm and exposes `get_label(text)` for one text or a batch; it is the same package and the same `y_pred` convention `bootstrap_compare.py` scores.
6. `score(hyp, ref)` — `rouge_l_score(hyp.split(), ref.split())`, `corpus_bleu([hyp],[ref],1)` and `4`, CheXbert-14 per-sample micro-F1 and exact match from the two label vectors via `bootstrap_compare.chexbert_f1`. Same tokenisation as the thesis tables, so a number shown here is comparable to them.

**Concurrency and cost.** One `ThreadPoolExecutor(max_workers=1)` serialises inference; the API accepts up to 4 queued turns and answers `overloaded_error` beyond that. Expected per-turn wall on 8 cores, fp32: encode 0.5–1 s, retrieve <0.1 s, cached beam-3 for 100 tokens 3–6 s, label 0.2 s. Note from the code read: exact TFLA falls back to a sequential intra-chunk loop whenever any dimension's chunk log-decay is extreme, so real per-token cost is measured in P1, not assumed.

**Streaming from the beam.** The callback is the only hook needed:

## 6. Frontend walkthrough

A single HTML page, one CSS file and four ES modules (about 1,200 lines in total), served by FastAPI at `/` so origin and API match; no framework, no bundler, no CDN dependency, so it also works when the laptop is offline behind the SSH tunnel. Look and feel follows the assistant-UI conventions the user already knows: a left sidebar of sessions, a centred conversation column, a composer pinned to the bottom, a right-hand details drawer.

| Module | Responsibility |
| --- | --- |
| `index.html`, `styles.css` | layout grid, light/dark via `prefers-color-scheme` and CSS variables, the permanent "Research prototype — not for clinical use" banner |
| `api.js` | `fetch` wrappers, bearer token from `localStorage`, the streaming reader below, polling fallback, `X-Request-Id` capture |
| `state.js` | in-memory store: sessions, messages, events; pure reducers so replaying stored events rebuilds the exact view |
| `render.js` | DOM builders for every card; a message is re-rendered from its event list, never patched ad hoc |
| `app.js` | wiring: routing (`#/s/<session_id>`), composer, drag-drop and paste of images, keyboard shortcuts, settings drawer |

**Conversation column.** A user turn shows the thumbnail (client-side downscaled to 512 px for display; the original bytes go to the server), the text, and the resolved options as small chips. An assistant turn is one card with four regions:

- **Stage timeline** at the top: a horizontal strip of six steps (`preprocess › encode › retrieve › generate › label › score`) that light up as `stage_end` events arrive, each with its milliseconds; clicking a step expands its `detail` JSON as a readable table. Skipped stages are greyed with the reason.
- **Report**: rendered as "Findings" and "Impression" sections (split on the literal headers the model emits), monospace-free, with a copy button, a "show raw" toggle, a `display_repair` toggle, and a truncation notice when `truncated_mid_sentence` is true. During decoding the current best beam is shown with a subtle "provisional" style, since earlier text can change.
- **Labels**: the 14 CheXbert chips in the canonical order, positives filled, negatives outlined; when a reference exists, agreement is colour-coded per label and the `score` numbers sit beside them.
- **Neighbours**: `retrieval_k` cards with similarity bars; in private mode each expands to the retrieved report and its labels, in public mode only the bar is shown.

A footer line carries provenance (model, checkpoint short hash, operators, `prefix_k`, decode settings, total ms) and links to `GET /v1/models`.

**Composer.** Textarea with Enter to send and Shift+Enter for a newline, an image well that accepts click, drag-drop and paste, the current settings as chips, and a Stop button that aborts the `fetch` (the server finishes the stage it is in and stores the partial message as `status=aborted`). In private mode a "Test-split study" picker lets you choose a study id from `test.parquet`; the server loads the image and the reference itself, so the demo of generated vs reference vs retrieval floor is one click.

**Streaming client.** `EventSource` is not used (it cannot send a bearer header and it does not stream through a quick tunnel); the reader parses SSE frames from a `POST` body:

```javascript
// api.js (sketch)
export async function* streamTurn(sessionId, form, token, signal) {
  const res = await fetch(`/v1/sessions/${sessionId}/messages`, {
    method: 'POST', body: form, signal,
    headers: token ? { Authorization: `Bearer ${token}` } : {} });
  if (!res.ok) throw new Error(`${res.status} ${await res.text()}`);
  const reader = res.body.getReader(), dec = new TextDecoder();
  let buf = '';
  for (;;) {
    const { value, done } = await reader.read();
    if (done) return;
    buf += dec.decode(value, { stream: true });
    let i;
    while ((i = buf.indexOf('\n\n')) >= 0) {           // one SSE frame
      const frame = buf.slice(0, i); buf = buf.slice(i + 2);
      const ev = /^event: (.*)$/m.exec(frame)?.[1];
      const data = frame.split('\n').filter(l => l.startsWith('data: ')).map(l => l.slice(6)).join('\n');
      if (ev) yield { event: ev, data: JSON.parse(data) };
    }
  }
}
```

The caller dispatches each event to `state.js`; a watchdog switches to `GET /v1/messages/{id}?after=<seq>` polling if no bytes arrive for 3 s and the message is still `running`.

**Sessions.** The sidebar lists sessions newest first with title (first user text or the upload filename), date and turn count; opening one fetches `GET /v1/sessions/{id}` and replays its events through the same reducers, so a replayed message is pixel-identical to the live one. Export offers JSON (the raw event log) and Markdown (report, labels, neighbours, provenance per turn). Delete asks once and calls `DELETE`.

**Settings drawer.** Model, decode, beam size, token budget, cached decode, compile, retrieval k, labelling on/off, display repair, mode indicator (read-only, from `/healthz`), API base URL and token (for the GitHub Pages variant). Settings persist in `localStorage` and are sent with every turn, so the server never holds UI state.

## 6a. Image input, display and retrieval

The chat takes an X-ray, shows it back everywhere it is used, and adds two retrieval views that carry images: similar training X-rays (image→image) and best-matching reports (image→report, the retrieval chapter's own capability). For a test-split study it also shows where the patient's true report ranks — R@10 made visible for one image.

**What the user sees in each turn**

- **Their upload**, in the user turn, served back by the server (`/v1/messages/{id}/image?variant=thumb`), so a reload, a replayed session or another device still shows it. Clicking opens a full-size viewer: zoom, pan, brightness/contrast (CSS filters, display only), original pixel size.
- **Model input**, in the assistant card: the exact 224×224 image the tower saw after resize and grayscale→3-channel, beside the original, so a crop or aspect problem is visible.
- **Similar X-rays**: a grid of `k_images` neighbour thumbnails with rank and cosine similarity; each opens side by side with the query in the viewer. Each neighbour carries its report's 14 CheXbert labels and their agreement with the generated report's labels — the visible check that "similar" means clinically similar, not only visually.
- **Matching reports**: the top `k_reports` reports ranked by image→report similarity, with rank and score. For a test-split study a badge shows the true report's rank (for example `The patient's own report ranks 3 of 194,125`).

**Where the embeddings come from.** Both views use the 13D contrastive checkpoint `h100_kd_150m_v2_full_data_lr3e6/last.ckpt`, which holds both halves of the retrieval chapter's joint model. The image half is the tower the decoder already uses (its `image_encoder.*` keys; pooled 512-d, L2-normalised). The text half is the `HybridTextEncoder` (`hybrid_150m_v2` with the operators it was trained with, plus its projection head; the `model.*` keys), loaded with the loaders in `scripts/evaluate_cxr_retrieval.py`. Reports are embedded in the training format, `Findings: … Impression: …`. Stock BiomedCLIP is not used here; the published retrieval floor did use it, so the demo labels its neighbours "13D tower" to keep the two apart.

**Gallery, built once.** `scripts/build_retrieval_gallery_h100.sh` writes, next to the sessions directory on restricted storage:

| File | Contents |
| --- | --- |
| `img_emb.npy` | train-split image embeddings, float16, one row per study (191,462 × 512) |
| `txt_emb.npy` | report embeddings for the train and test splits, float16, one row per unique report group |
| `meta.json` | row → study id, subject id, split, image path, report hash, report group, CheXbert-14 labels |
| `thumbs/` | 256 px JPEG per gallery image, so the server never resizes on the fly |
| `manifest.json` | SHA-256 of the tower and text-encoder weights, row counts, build date, git SHA; the server refuses a gallery whose tower hash differs from the loaded decoder's tower |

Identical reports are common in MIMIC, so report ranking works on unique report groups (the retrieval chapter's dedup-aware convention in `evaluate_cxr_retrieval.py`), and the displayed list shows each group once. The true report's rank follows that script's convention: the position of the first report in its group, counting every report row, so it agrees with the chapter's R@k. Test-split images are never in the image gallery, so a test-split query cannot match itself; an upload whose pixels hash to a gallery image is flagged "identical to a gallery image".

**Privacy.** Neighbour images, study ids and report text are MIMIC data and appear in private mode only; in public mode both views keep similarity scores and label chips and drop images, ids and text. A user's own upload is shown back to that user in both modes. Every MIMIC-derived image response carries `Cache-Control: no-store`.

**Contract changes.** `retrieval_k` is replaced by `k_images` (default 4, range 0–12) and `k_reports` (default 3, range 0–10). Three endpoints are added to §4: `GET /v1/messages/{id}/image?variant=original|thumb|model_input`, `GET /v1/gallery/images/{row}` (private only), and `POST /v1/retrieve`, which now returns both views without generating. The `retrieve` stage's detail becomes:

```
{"image_neighbors":[{"rank":1,"similarity":0.913,"gallery_row":1843,
                     "image_url":"/v1/gallery/images/1843","study_id":"5041…",
                     "labels":{…},"label_agreement":0.86}, …],
 "report_matches":[{"rank":1,"similarity":0.412,"group":"g_88213",
                    "report":"Findings: …","labels":{…}}, …],
 "true_report_rank":3,
 "gallery":{"images":191462,"report_groups":…,"tower_sha256":"…"}}
```

In public mode `image_url`, `study_id`, `report` and `true_report_rank` are absent.

## 7. Storage and session recording

One SQLite file in WAL mode plus two directories, all under `/sc/home/$USER/chat_sessions/` (restricted storage, never under the repo tree, backed up by whatever backs up home). No ORM: the stdlib `sqlite3` module, four tables, and every write inside a transaction. The event log is the source of truth; the message row's `report` column is a convenience copy.

| Table | Columns | Notes |
| --- | --- | --- |
| `sessions` | `id` (ULID), `created_at`, `updated_at`, `title`, `mode`, `deleted_at` | `mode` is the server mode at creation; soft delete first, files removed by the same call |
| `messages` | `id`, `session_id`, `seq_in_session`, `role` (`user`/`assistant`), `created_at`, `text`, `image_path`, `image_sha256`, `options_json`, `status` (`running`/`done`/`error`/`aborted`), `report`, `display_report`, `provenance_json`, `total_ms` | one assistant row per user row; `image_path` points into `uploads/<session>/<sha256>.png` so a re-used image is stored once |
| `events` | `message_id`, `seq`, `ts`, `event`, `data_json` | the exact frames sent to the client; `PRIMARY KEY(message_id, seq)` |
| `artifacts` | `message_id`, `kind` (`neighbor_report`/`reference`/`labels`/`dump`), `path`, `restricted` (bool) | anything MIMIC-derived is flagged `restricted=1` and excluded from public-mode exports |

**Write path.** `POST .../messages` inserts the user row and an `assistant` row with `status=running` before the pipeline starts; each event is written, committed, then sent; `message_stop` updates `status`, `report`, `total_ms`. A crash mid-turn leaves a `running` row that the next server start marks `error` with `reason=server_restart`. A client abort leaves `aborted` with whatever events had landed.

**Export.** `?format=json` returns the session, its messages and their event lists verbatim; `?format=md` renders each turn as a heading, the report, a label table, the neighbours (private mode only) and a provenance line. Exports are generated on request, never cached.

**Retention and privacy.** Uploads are the only user-supplied medical images the system holds; they stay on the cluster, are never included in exports, and a nightly `sbatch` job (or the server at start-up) deletes sessions older than `RETENTION_DAYS` (default 30, public mode 7). The public UI states this on the banner. Test-split images and reference reports never enter `uploads/`: the server reads them from the dataset directory by `study_id` and stores only the id.

**Size.** A turn stores roughly 110 events (about 40 KB of JSON, dominated by beam snapshots) plus the image; 1,000 turns is about 40 MB of database and 1–2 GB of PNGs, well inside the home quota.

## 8. Serving on the cluster, tunnels, and the laptop dev loop

Three ways to run the same code, chosen by one flag: `--engine tiny` on the laptop with random weights and no data, `--engine real --mode private` as a cluster job you reach over SSH, and the same job with `--mode public` behind a Cloudflare quick tunnel from the laptop. The cluster job is the only place the real checkpoint is ever loaded.

**The server job.** CPU only, following the repo's cluster invariants (`--partition=aisc-batch --account=aisc`, no `--gres`, `--exclude=ga03,gx17v1,gx13v1`, `--requeue`, `--open-mode=append`):

```bash
# scripts/serve_chat_h100.sh (header)
#SBATCH --partition=aisc-batch --account=aisc --qos=aisc
#SBATCH --cpus-per-task=8 --mem=32G --time=2-00:00:00
#SBATCH --exclude=ga03,gx17v1,gx13v1 --requeue --open-mode=append
#SBATCH --job-name=chat_server --output=logs/%x_%j.log --error=logs/%x_%j.log
set -euo pipefail
export HF_HUB_OFFLINE=1 PYTHONUNBUFFERED=1 OMP_NUM_THREADS=8
export TORCHINDUCTOR_CACHE_DIR=/sc/scratch/$USER/chat_inductor
echo "$(hostname):8000" > "$HOME/chat_sessions/endpoint"          # the tunnel script reads this
(.venv_chexbert/bin/uvicorn app.labeler:app --host 127.0.0.1 --port 8001 &)   # own venv, loopback only
.venv/bin/uvicorn app.server:app --host 0.0.0.0 --port 8000 --workers 1      # one process, one model
```

The API binds the node's interface so the login node can forward to it; the labeler binds loopback because only the API calls it. `--workers 1` is deliberate: one model in memory, one inference executor. A SIGTERM from preemption is trapped in `app/server.py` to commit the SQLite transaction and mark running turns; `--requeue` brings the job back on another node and the endpoint file changes.

**Reaching it from the laptop.** Nothing is executed on `lx01` except single commands, which the cluster allows; the loop lives on the laptop:

```bash
# app/tunnel/tunnel.sh (essentials)
LOGIN=${LOGIN:-lx01}
while true; do
  EP=$(ssh "$LOGIN" 'cat ~/chat_sessions/endpoint 2>/dev/null')      # node:port written by the job
  NODE=${EP%%:*}
  ssh -N -o ExitOnForwardFailure=yes -o ServerAliveInterval=30 \
      -L 8000:"$NODE":8000 "$LOGIN"                                  # returns when the job moves or dies
  sleep 15                                                            # then re-read the endpoint
done
```

`http://localhost:8000` on the laptop is now the app. The SPA polls `/healthz` and shows a "server restarting" strip while the forward is down. If the job has ended, `ssh lx01 sbatch scripts/serve_chat_h100.sh` resubmits it — again a single command, so it passes the login-node guard.

**Public demo.** On the laptop, `cloudflared tunnel --url http://localhost:8000` prints an `https://<words>.trycloudflare.com` URL; the job must have been started with `--mode public` and a non-empty `APP_TOKEN`, and the URL plus token are shared out of band. Known limits from §2: no uptime guarantee, 200 requests in flight, `GET` responses buffered (why the stream is a `POST` and polling exists). Stop `cloudflared` when the demo ends. A named tunnel with Cloudflare Access is the upgrade if a domain becomes available; nothing in the code changes for it.

**Laptop dev loop, no weights, no data.** `python -m app.server --engine tiny` builds the same tiny random-init model `evaluate_report_generation.py --smoke-test` uses (`dim=32`, two layers, `["mamba3","mlstm"]`, `tfla_impl=exact` so the cached path is exercised), a random `ImagePrefixMapper`, a 1,000-row random gallery, and a rule-based stand-in labeler that flags a few keywords. Every endpoint, every event type and the whole UI run in under a second per turn, so P2–P4 and their tests never need the cluster. `--engine mock` replays a recorded event log for pure front-end work. Nothing MIMIC-derived is needed or allowed in this mode, which is also what CI would run if the repo ever gets CI again.

**Pre-staged assets on the cluster (once).** BiomedCLIP and the GPT-2 tokenizer are already in the HF cache the eval jobs use; the CheXbert weights are in the chexbert venv from `setup_chexbert_venv_h100.sh`; the retrieval gallery is built by `scripts/build_retrieval_gallery_h100.sh` (one CPU-or-GPU job over `train.parquet`, \~30 min on an H100, longer on CPU) and written next to the sessions directory with the tower hash in its metadata.

## 11. Risks, cost and open questions

The cost is zero in money and roughly half an H100-hour once; the risks are the data-use agreement, the cluster's serving limits and the model's own behaviour, in that order.

| Risk | What it would break | Early warning | Mitigation |
| --- | --- | --- | --- |
